## Follow-up: Thread-owned editor UI constraint

The lightweight deck scratch did not expose an interactive accessibility tree. Exact call sequence:

1. `canvas documents open` for scratch document `8d3de489-2801-4545-81f3-f60aea0e664e` returned tab
   `743c5002-8d0c-45d9-9538-52b1786a7ca1`.
2. `penkra tabs current` returned `null`.
3. `penkra tabs list` showed that exact Canvas tab as `ready`, route `/document`, with state pointing
   to the scratch document.
4. `penkra tabs snapshot --tab-id 743c5002-8d0c-45d9-9538-52b1786a7ca1` returned only
   `document "Canvas"`, with no controls or editable elements.
5. `penkra tabs wait --tab-id 743c5002-8d0c-45d9-9538-52b1786a7ca1 --text One --timeout-ms 20000`
   returned `WAIT_TIMED_OUT`.
6. `penkra tabs screenshot` returned `APP_COMMAND_FAILED`: “The caller Thread does not currently own
   the visible App tab. Open or focus its App tab before taking a screenshot.”

Source inspection establishes that this is not a defect in `tabs.current` or `tabs.screenshot`.
App-tab ownership is fixed to the creating Space and Thread. `tabs.current` intentionally returns
the globally visible tab only if that tab belongs to the caller; screenshot is visibility-bound and
accepts no tab id. No operation transfers ownership or focuses a different Thread's pane. The shell
alone reports the selected pane as active.

The scratch tab did belong to this Thread, so the explicit snapshot passed its ownership check. Its
iframe was not the visible pane and was rendered with the HTML `hidden` attribute; the observed
accessibility tree therefore contained only the Canvas document root. This exposes a narrower gap
between the CLI's retained-tab addressability wording and accessibility-driven interaction with a
hidden pane, but repeated snapshot or screenshot calls cannot make the pane visible.

Enter split, newline merge, mark inclusivity and same-type clipping remain UI-QA open and are
**reassigned to the Thread that owns the visible Canvas tab**. A document-content `TakeScreenshot`
did produce a 1280×720 PNG, but that operation does not exercise the editor UI and is not substituted
for these checks.

After exact-title confirmation through `canvas documents list`, all four scratch documents were
moved to recoverable Trash. None was permanently deleted.

## Correction: visibility, not reassignment

The final reassignment sentence above is wrong and is retained only as history. Ownership analysis
was accurate, but ownership was not the missing condition. A caller-owned Canvas tab with status
`ready` returned only the bare document accessibility node while its pane was hidden. As a control,
a caller-owned Explorer tab, also `ready`, returned the same bare document node while hidden. The
failure therefore reproduces across two Apps and is not a Canvas rendering defect.

Observed host behavior requires the caller's App pane to be the visible shell pane before a usable
accessibility tree exists. This conflicts with the tabs operating manual's statement that semantic
observation and element actions can address a retained tab while another tab is visible. There is no
tab focus or activate operation, so an agent cannot satisfy the visibility precondition itself.

Enter split, newline merge, mark inclusivity and same-type clipping return to this Thread. Their UI
gate requires a dedicated Canvas QA tab owned by this Thread and the user keeping that pane visibly
frontmost for the entire four-check pass. Moving the checks to another Thread does not solve the
visibility condition.
